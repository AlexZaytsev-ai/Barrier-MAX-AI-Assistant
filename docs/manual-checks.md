# Ручная проверка после настройки

Это план проверок для публичной копии; отметки об их выполнении в новой среде отсутствуют.

| Сценарий | Что проверить |
| --- | --- |
| Обычный вопрос о дверях | Ответ приходит в личный чат; пара user/assistant сохраняется в PostgreSQL. |
| Уточнение с учётом истории | Модель получает предыдущие сообщения в хронологическом порядке; не начинает консультацию заново. |
| «Позовите сотрудника» | В группу приходит запрос с ID клиента и историей; режим меняется на waiting; покупатель получает подтверждение передачи. |
| Сообщение в waiting | Сообщение пересылается в группу и сохраняется; ИИ молчит. |
| Reply сотрудника на сообщение бота | Ответ приходит нужному покупателю; режим становится human; текст сохраняется в истории с пометкой сотрудника. |
| Сообщение покупателя в human | Сотрудники получают сообщение; ИИ не отвечает. |
| Обычный текст сотрудника в группе | Покупатель не получает сообщение без Reply. |
| Reply на сообщение другого человека | Проверка автора исходного сообщения отклоняет ответ. |
| Reply без текста или ID покупателя | Ветка отправки покупателю не выполняется. |
| «Вернуться к ИИ» | Режим становится ai; следующее сообщение обрабатывает модель. |
| Поздний Reply после возврата к ИИ | Ответ сотрудника доходит; режим ai не заменяется на human. Отдельно проверить одновременные события. |
| Запрос на замер или установку | Обращение передаётся сотруднику; дата и время не объявляются подтверждёнными без его ответа. |
| Посторонняя тема | Бот возвращает разговор к дверям и услугам магазина. |
| Наличие конкретной модели | Бот не выдумывает остатки и предлагает проверку сотрудником. |
| Неверный секрет webhook | Входящий запрос не должен запускать рабочую ветку. |

Дополнительно проверьте недоступность PostgreSQL, ошибки OpenAI/MAX, повторную доставку события и параллельные сообщения. Эти сценарии нужны для выявления ограничений: текущий экспорт не гарантирует retry, дедупликацию и сериализацию событий.
